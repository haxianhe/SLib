# code-investigation：代码实现全景调查

> 一次 grep 只能告诉你"在哪出现"。**全景调查让你看清一个功能的全貌** —— 哪些类参与、怎样流转、如何配置、为何这样设计。看完后能快速上手修改，也能判断改动影响面。

---

## 调查目标

给定一个关键词/功能名/模块名，产出一份**结构化报告**，覆盖：

1. 核心类清单（定义在哪、各自职责）
2. 主要流程（生成/创建流、验证/消费流、异常流等）
3. 配置项（默认值、来源、热加载方式）
4. 设计要点（架构决策、取舍说明）
5. 边界区分（与相似/易混淆模块的差异）

---

## 执行步骤

### Phase 1：广度搜索

对目标关键词做多维度 grep/find，覆盖：

- 类名/接口名（PascalCase、camelCase）
- 文件名（kebab-case、snake_case）
- 注解/装饰器中的引用
- 配置文件中的键名
- 测试文件

搜索范围不限于单一目录，要跨模块扫描。记录所有命中的 `file:line`。

### Phase 2：分类归档

将搜索结果按职责分类：

| 类别 | 判断依据 |
|------|----------|
| 定义层 | 接口/类/DTO/枚举的声明 |
| 业务逻辑层 | Service、Handler、Processor |
| 接入层 | Controller、Filter、Interceptor、Middleware |
| 配置层 | Config、Properties、环境变量 |
| 存储层 | Repository、DAO、Cache、Store |
| 测试 | Test、Spec 文件 |

### Phase 3：流程追踪

从接入层入口开始，顺着调用链追踪主要流程：

- 识别入口点（HTTP endpoint、RPC 接口、消息监听器）
- 逐层追踪调用关系
- 标注关键决策分支
- 记录异常/降级路径

### Phase 4：配置收集

汇总所有相关配置项：

- 配置键名
- 默认值
- 来源（文件/环境变量/配置中心/代码硬编码）
- 是否支持热加载
- 影响范围

### Phase 5：输出报告

## 输出格式模板

严格按以下结构输出，每个 section 必须存在（无相关内容时写"无"）：

```markdown
## [功能名] 实现全景

---

### 核心类

| 文件 | 职责 |
|---|---|
| `path/to/FileA.java` | 一句话描述 |
| `path/to/FileB.java` | 一句话描述 |
| ... | ... |

---

### [流程名1]流程

\```
入口描述
  → 第一步 (关键细节)
    → 第二步 (关键细节)
      → 第三步 (关键细节)
    → 返回/输出
\```

### [流程名2]流程

\```
入口描述
  → ...
\```

---

### 关键配置

| 字段 | 默认值 | 说明 |
|---|---|---|
| `configKey` | `value` | 一句话 |
| ... | ... | ... |

---

### 设计要点

1. **要点标题** — 具体说明
2. **要点标题** — 具体说明
3. ...

---

### 边界区分

说明本功能与项目中其他相似/易混淆模块的区别。如果不存在易混淆模块，可省略此节。
```

---

## 质量标准

- **完整性**：不遗漏核心参与者。宁可多列一个"可能相关"的文件，也不要漏掉实际参与的类。
- **准确性**：每个 `file:line` 必须基于实际搜索结果，不可凭记忆编造路径。
- **简洁性**：表格和流程中每条描述控制在一句话以内。详细解释放在设计要点中。
- **可操作性**：看完报告后，读者应能立即知道"改 X 需要动哪些文件"。

---

## 适配不同语言/框架

本 skill 不限定具体技术栈。根据项目实际情况调整：

- **Java/Spring**：关注 Controller → Service → Repository 分层、Filter/Interceptor 链、配置中心（Diamond/Nacos/Apollo）
- **TypeScript/Node**：关注 Router → Handler → Middleware 链、env 配置、依赖注入容器
- **Python**：关注 View → Service → Model 分层、装饰器、settings 文件
- **Go**：关注 Handler → Service → Repository、middleware 链、config struct

---

## 注意事项

- 搜索时同时覆盖 main source 和 test source
- 对于多模块项目（Maven multi-module、monorepo），明确标注每个文件所属模块
- 如果功能涉及外部依赖（RPC、消息队列、缓存），在设计要点中说明依赖关系
- 流程图用缩进箭头（`→`）表示调用深度，不要用 ASCII art 方框图（太占空间且不易阅读）
- 配置表中对敏感值（密钥、token）只标注"从配置中心获取"，不展示实际值
