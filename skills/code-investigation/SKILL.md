# Code Investigation

对一个功能做证据驱动的只读全景调查。目标是回答“在哪里、怎样流转、如何配置、为什么这样设计、改动会影响什么”。

## 只读边界

调查阶段只允许搜索、读取、静态分析和不改源码的验证命令。不得编辑代码、运行会重写文件的格式化或生成命令，也不得安装依赖。

用户同时说“看到问题顺手改掉”时：

1. 先完成调查并把问题列入报告。
2. 明确区分事实、推断和建议。
3. 修复属于新的实施任务；取得明确授权并切换到相应开发流程后才能修改。

## 调查流程

### 1. 定义范围

记录功能名、同义词、可能的类名/配置键、仓库范围和排除项。关键词有歧义时先通过目录和定义位置收敛，不凭名称猜模块。

### 2. 广度搜索

同时搜索：

- 类、接口、函数、DTO、枚举和文件名；
- 路由、注解、装饰器、注册表和依赖注入；
- 配置文件、环境变量和默认值；
- 存储、缓存、消息、外部服务；
- 单元、集成和端到端测试。

优先使用仓库已有的快速搜索工具。保存有意义的 `file:line` 证据；不要把生成目录或依赖目录的大量命中当作实现证据。

### 3. 分类与深读

按定义、接入、业务、存储、配置、外部集成和测试分类。选择入口和关键实现深读，确认职责，不根据文件名推断。

### 4. 追踪流程

从真实入口追踪：

- 正常创建/读取/消费流程；
- 状态转换和关键决策分支；
- 异常、重试、降级和回滚；
- 异步消息、定时任务和动态注册；
- 数据持久化及外部边界。

遇到反射、代码生成、运行时注册或调用链中断时，明确标为“待运行时验证”，不要补全不存在的静态证据。

### 5. 汇总配置与影响面

记录配置键、默认值、来源、热加载能力、影响范围和敏感性。密钥和 token 只说明来源，不显示实际值。

## 异常处理

- 零命中：列出搜索词和范围，请用户确认命名或分支。
- 同名实现：分别报告并说明选择主链路的证据。
- 权限不足、文件不可读或输出截断：列出未覆盖范围，降低结论置信度。
- 大型仓库：先按模块分片，再合并证据；不要因为时间压力宣称“全量覆盖”。

## 报告格式

```markdown
## {功能名} 实现全景

### 调查范围与结论
- 范围：
- 一句话结论：
- 未覆盖/待确认：

### 核心文件
| 文件与行号 | 分类 | 职责 | 证据 |
|---|---|---|---|

### 调用与状态流程
入口 → 业务决策 → 存储/外部边界 → 返回

### 异常与降级流程
| 触发条件 | 处理 | 最终状态 | 证据 |
|---|---|---|---|

### 关键配置
| 字段 | 默认值 | 来源 | 热加载 | 影响范围 |
|---|---|---|---|---|

### 设计要点与边界
- 已确认事实：
- 基于证据的推断：
- 与相似模块的区别：

### 发现的问题与改动影响
| 严重度 | 问题 | 证据 | 建议 | 可能影响 |
|---|---|---|---|---|
```

没有内容的章节写“未发现”，不要省略。所有路径和行号必须来自当前工作树；报告结束时重申本次是否保持只读。
