# 提纲式技术方案写作

写成可快速扫描的方案说明：按领域分层，以具体机制说明能力，用准确措辞表达责任与边界。风格迁移只迁移表达规则，不迁移参考文章的业务事实。

## 写作流程

1. 从用户材料提取主体、对象、机制、效果、限制和实施状态。区分已实现、测试中、拟实施、待确认；未说明状态时使用中性描述，不能改写为“已完成”。
2. 按材料实际涉及的能力或治理领域划分章节，使用 `## 一、领域名称`。不固定章节数量，不照搬示例领域，不为凑结构补充功能。
3. 每条使用 `- **短标签：** 正文`。标签概括一个控制点；正文通常一至三句话，优先表达“主体 + 机制或动作 + 对象 + 约束或效果”。缺少的要素不强行补齐。
4. 直接进入方案。只有理解范围确有需要时才加一两句开场。默认不追加评审问题清单、总结口号或写作过程；用户要求或存在影响结论的缺口时，再简短列出待确认项。
5. 末尾仅在确有可引用材料时添加“参考文档”。缺少资料时不虚构引用；脱敏输出不保留内部来源链接。

## 表达与排版

| 维度 | 写法 |
|---|---|
| 语气 | 正式、克制、直接；使用校验、绑定、处理、记录、拒绝等具体动词 |
| 论述 | 说明谁处理什么、经由何种机制、在什么条件下生效；材料提供异常行为时准确保留 |
| 强度 | 原材料有明确规则才使用“不得”“仅允许”“方可”；不能把建议提升为强制要求 |
| 效果 | 使用有依据的具体效果；无证据时不宣称“全面保障”“彻底杜绝”或“符合全部法规” |
| 术语 | 保留必要通用技术术语；对影响理解的术语简短解释，不展开基础教程 |
| 强调 | 标签加粗，一般关键机制酌情加粗；核心原则、操作前提与禁止项优先强调，避免整句整段高亮 |

默认使用兼容 Markdown，不输出用于模拟颜色的 HTML。用户要求富文本且目标支持时，标题与标签用深色，正文灰黑，核心约束暗红色加粗（可用 `#BB2626`），参考链接蓝色。颜色不得是唯一的信息载体。

## 脱敏

技能本体、元数据和示例只使用通用角色与虚构材料，不保存参考原文、内部链接、来源标题或真实名称映射。

用户要求脱敏或公开复用时，对正文、标题、链接文字、链接目标、代码、图片说明和附录统一处理：

- 将组织、客户、平台、项目代号、专有组件改成一致的角色称谓，如“业务服务”“接入网关”“审批平台”。不同责任主体不能合并成同一个模糊称谓。
- 删除不影响技术理解的姓名、联系方式、账号与租户标识、内部域名、文档 ID、路径、密钥和凭证值。不要保留可逆映射表，也不要在脱敏说明中复述原值。
- 对可用于关联识别的精确日期、规模和专用字段名，按需要删除、泛化或替换为语义名称；保持调用关系、前提条件和实施状态不变。
- 若精确参数本身决定技术结论，不能悄悄改成另一个值。用“阈值已隐去”等方式标示，并说明无法据此复核的结论。
- 脱敏不等于删除限制和失败行为；不可因此把方案描述得更成熟、更安全。

仅要求内部材料润色时，按用户指定范围脱敏，不擅自删除其必须保留的业务信息。写作本身不要求上传材料、搜索外网或发布文档。

## 虚构示例

输入事实：客户端提交任务；任务服务校验参数，不完整时返回错误；队列仅用于测试环境；拟在上线前增加重试上限，次数未定。

输出：

```markdown
## 一、任务接入

- **参数校验：** 任务服务校验客户端提交的任务参数，**参数不完整时返回错误**。

## 二、执行管理

- **队列使用：** 当前队列**仅用于测试环境**。
- **重试约束：** 拟在上线前增加重试次数上限，具体次数待确认。
```

## 交付前检查

- 只读标题与标签，能否理解主要能力和责任分工？
- 每条是否聚焦一个控制点，且事实、状态与约束强度均有材料依据？
- 是否把未知后续流程补写成了事实，或擅自新增评审要求？删除这些补写。
- 是否残留专名、内部链接、唯一标识或能恢复身份的映射？脱敏时一并处理。
- 是否按目标支持的格式输出，且重点不过度、参考资料真实可用？
